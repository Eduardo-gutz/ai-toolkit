# Conventions: generate `.context/conventions.md`

You are an AI agent. Your job is to generate **a single file** in the
target repo: `.context/conventions.md`.

**This step is OPTIONAL.** The conductor asks the developer first. If the
developer said no, this step does not run.

## Inputs

- Target repo: path of the repo to initialize.
- Standards JSON: the complete JSON produced by `03-standards.md`. You
  especially need `standards.cross_cutting.*` and `standards.product.*`.
- Stack id: the `stack_id` the standards JSON was normalized against.

## Output

**A single file**: `<repo>/.context/conventions.md`.

If the file already exists, **ask the user** before overwriting (show
them a proposed diff section by section).

## Absolute rules

- **Every asserted value carries its provenance marker.** The legend is
  written once, at the top of the file:

  ```markdown
  > Provenance legend — `[confirmed]`: the developer stated it in the
  > interview. `[default: <file>]`: it comes verbatim from the stack
  > defaults catalog. `[pending]`: undecided — the value is `null` and it
  > is listed in `open_questions`.
  ```

  Then every line that asserts a value renders its marker, for example
  `structured logger — [confirmed]`,
  `schema validation at the boundary — [default: defaults/_baseline.md]`
  or `Authentication — [pending]`.
- A `[default: …]` marker MUST name the catalog file the value came from.
- A `[pending]` line MUST show the value as `not decided` — never a
  placeholder guess.
- **A section whose field is `[pending]` is still written** — with the
  `not decided — see open_questions` marker. The developer needs to see
  what is still open.
- Do not invent contracts. A response envelope, a header name or an auth
  mechanism that no confirmed value describes does not exist yet.
- Do not add emojis.
- The file must be **100% derivable from the standards JSON**.

## Expected output structure

The `.context/conventions.md` file must have this structure (in this
order). Omit a section only when the stack cannot have it at all (for
example a `Response format` section in a project with no HTTP surface) —
never because the value is undecided.

### Internationalization, caching, feature flags, rate limiting

One subsection per concern, each stating the approach with its marker, or
`not decided — see open_questions` when the field is `[pending]`.

### Documentation, accessibility, license, performance budget

One subsection per concern, each stating the policy with its marker, or
`not decided — see open_questions` when the field is `[pending]`.

## How to derive each section

Each section maps to exactly one `standards.cross_cutting.*` or
`standards.product.*` leaf:

| Section | Field |
|---------|-------|
| Response format | `standards.cross_cutting.errors` |
| Authentication | `standards.cross_cutting.auth` |
| Logging | `standards.cross_cutting.logging` |
| Validation | `standards.cross_cutting.validation` |
| Internationalization | `standards.cross_cutting.i18n` |
| Caching | `standards.cross_cutting.cache` |
| Feature flags | `standards.cross_cutting.feature_flags` |
| Rate limiting | `standards.cross_cutting.rate_limiting` |
| Documentation | `standards.product.documentation` |
| Accessibility | `standards.product.accessibility` |
| License | `standards.product.license` |
| Performance budget | `standards.product.performance_budget` |

Take the value verbatim, with its marker. Expand it into the concrete
rules the section lists, but never beyond what the value implies. When
the value is `[pending]`, write `not decided — see open_questions` and
leave the sub-bullets empty.
