# Code style: generate `.context/code-style.md`

You are an AI agent. Your job is to generate **a single file** in the
target repo: `.context/code-style.md`.

## Inputs

- Target repo: path of the repo to analyze.
- Discovery JSON: the complete JSON produced by `02-discovery.md`. You
  especially need `conventions_observed`, `samples`, `repo` (for
  `linter` and `formatter`).

## Output

**A single file**: `<repo>/.context/code-style.md`.

If it already exists, **ask the user** before overwriting (proposed
diff section by section).

## Absolute rules

- Do not invent: if you did not find a pattern in the code, declare it
  as "pending" or "not found".
- Do not copy conventions from other projects. Analyze ONLY this repo.
- Do not add emojis.
- Cite real paths with `path/to/file:line`.
- Snippets must be **real** from the repo (copied or simplified from
  the cited original), not invented.

## How to derive each section

### Linters and formatting

Use `repo.linter` and `repo.formatter` from the discovery JSON. Look
for the config files:

- ESLint → `.eslintrc*`, `eslint.config.*`.
- Prettier → `.prettierrc*`.
- Ruff → `ruff.toml`, `[tool.ruff]` in `pyproject.toml`.
- Black → `[tool.black]` in `pyproject.toml`.
- Go → no config needed, but verify `gofmt` runs in CI.
- Rust → `rustfmt.toml`.

For the command, look at the manifest `scripts`
(`package.json` → `scripts.lint`, `scripts.format`).

### Import order

Read 2-3 files from the repo and look at the order. If they are
separated by blank lines into groups (third-party, internal, etc.),
describe it that way.

### Naming conventions

Use `conventions_observed` as a starting point, but **verify with 3-5
real examples** per category. If the convention is not consistent,
mark it as "mixed" and list the variants.

### Code patterns

For each applicable category:

1. Use the discovery JSON sample (`samples.router`, `samples.service`,
   etc.).
2. If the sample is `null`, omit that category.
3. Read the full file (or at least the first 30-50 lines).
4. Copy a representative snippet of ~10 lines.
5. List the rules you can infer from the snippet.

### Error handling / Async / Logging / Validation

Use `cross_cutting` from the discovery JSON. For each applicable
concern:

1. Find the file where it is implemented (logger setup, error
   middleware, validator helper).
2. Copy a snippet of ~5-10 lines.
3. Describe the pattern in prose.

### Tests

Use `repo.test_framework` and `conventions_observed.test_naming`.
Look for the test runner config (`vitest.config.*`, `jest.config.*`,
`pytest.ini`, `[tool.pytest]` in `pyproject.toml`).

For mocking, look for `mock`, `vi.mock`, `jest.mock`, `unittest.mock`
and describe the pattern.

### Export style

Look for `export default` vs `export const` / `export function`. If
there is a mix, describe it.

### Comments

Look for blocks `/** ... */` (JSDoc), `"""..."""` (Python docstrings),
`// ...` (Go). Evaluate:

- Are they used consistently?
- Do they cover public functions, complex logic, or both?
- Is there a format (`@param`, `@returns`, etc.)?

## If the discovery JSON has empty or "unknown" fields

Do not invent. If `repo.linter` is `null`, write "not found" under
Linter. If `samples.service` is `null`, omit Service. If you cannot
infer the import order, say "not identified — review manually".
