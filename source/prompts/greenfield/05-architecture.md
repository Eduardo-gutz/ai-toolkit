# Architecture: generate `.context/architecture.md`

You are an AI agent. Your job is to generate **a single file** in the
target repo: `.context/architecture.md`.

## Inputs

- Target repo: path of the repo to initialize.
- Standards JSON: the complete JSON produced by `03-standards.md`. You
  especially need `standards.architecture.*` and `standards.product.*`.

## Output

**A single file**: `<repo>/.context/architecture.md`.

If the file already exists, **ask the user** before overwriting (show
them a proposed diff section by section).

## Absolute rules

- **Every asserted value carries its provenance marker.** The legend is
  written once, at the top of the file:

  ```markdown
  > Provenance legend — `[confirmed]`: the developer stated it in the
  > interview. `[default: <file>]`: it comes verbatim from the stack
  > defaults catalog. `[pending]`: undecided — the value is `null` and it
  > is listed in `open_questions`.
  ```

  Then every line that asserts a value renders its marker, for example
  `Feature-based — [confirmed]`, `src/<feature> — [default: defaults/_baseline.md]`
  or `Folder naming — [pending]`.
- A `[default: …]` marker MUST name the catalog file the value came from.
- A `[pending]` line MUST show the value as `not decided` — never a
  placeholder guess.
- Do not copy conventions from other projects. Use only the standards
  JSON and the catalog files.
- Do not add emojis.
- Cite real paths (verify they exist) — the paths you propose must be the
  paths the layout will actually create.
- The file must be **100% derivable from the standards JSON**.

## How to derive each section

### Structure type

Take `standards.architecture.structure_type` verbatim, with its marker.

### Folder tree

Derive the tree from `standards.architecture.module_layout`. The layout
values map to trees like these:

- `src/core + src/modules/<feature>` → `src/core/` + `src/modules/<feature>/`
- `src/app + src/core + src/modules/<feature>` → `src/app/` + `src/core/` + `src/modules/<feature>/`
- `app/core + app/modules/<feature>` → `app/core/` + `app/modules/<feature>/`
- `src/Core + src/Modules/<Feature>` → `src/Core/` + `src/Modules/<Feature>/`
- `Sources/<Feature>` → `Sources/<Feature>/`
- `app/src/main/java/<package>/<feature>` → `app/src/main/java/<package>/<feature>/`
- `src/<feature>` → `src/<feature>/{ui,domain,data}/`
- `src/<layer>` → `src/{ui,domain,data}/`
- `<package>/<module>` → `<package>/<module>/`
- `app/` at the root → `app/{routes,components}/`
- `custom` → whatever the developer described; if the interview did not
  describe one, mark the section `[pending]`.

When the layout is one of the catalog defaults, the catalog's
`### Module layout` prescribed pattern is the tree — copy it verbatim and
keep the layer it names. Do not re-derive a tree the catalog already
spelled out.

Show the tree as a fenced code block. It is a **plan**, not an existing
tree — say so in one line.

### Layers and responsibilities

One subsection per layer named by `standards.architecture.layer_flow`.
Each subsection states what the layer may contain and what it must not.

The layer names are folders, not abstractions: `routes → components →
hooks → helpers → interfaces` means the `routes/` folder, the
`components/` folder, and so on. Use the folder name as the subsection
title.

### Dependency direction

State `standards.architecture.dependency_direction` verbatim, with its
marker, and spell out the allowed arrows.

### File naming conventions

Take `standards.architecture.directory_conventions` for folders and
`standards.code_style.naming_files` for files, each with its marker.

### Module boundaries

Derive from the dependency direction: list the import arrows that are
allowed and the ones that are forbidden.

### Public surface

Name the entry point implied by the layout and what it exports. Keep it to
the minimum surface.

**The tree is the authority.** When the layout is one of the catalog
defaults, the catalog's `### Module layout` tree names the entry point —
read it from there. The table below is the fallback for a custom layout.
Note that one layout can serve two stacks with different entry points:

| Layout | Entry point |
|---|---|
| `src/core + src/modules/<feature>` | `src/index.ts` |
| `src/app + src/core + src/modules/<feature>` | `src/app/layout.tsx` (Next.js) · `src/app/_layout.tsx` (React Native, expo-router) |
| `app/core + app/modules/<feature>` | `app/main.py` (FastAPI) · `app/__init__.py` (a plain Python package) |
| `src/Core + src/Modules/<Feature>` | `public/index.php` |
